Software Engineering · Module 04

Software Design

Software design transforms the requirements described in the Software Requirements Specification (SRS) into a structured solution that can be implemented. This module covers design concepts and principles, modularity, functional independence, coupling, cohesion and architectural styles.

04.1 Introduction to Software Design

Software Design: The process of planning and defining a software solution by converting the requirements given in the SRS document into a design that guides implementation.

The purpose of the design phase in the Software Development Life Cycle is to produce a solution to the problem described in the SRS. The output of the design phase is the Software Design Document (SDD).

Objectives of software design

  • Convert user and system requirements into a technical blueprint.
  • Define the structure and components of the software.
  • Describe how components interact and exchange data.
  • Provide a basis for implementation, testing and maintenance.
  • Reduce complexity by organizing the system into understandable parts.
Exam point: The SRS describes what the system must do; the design describes how the system will be structured to meet those requirements.

04.2 Conceptual Design and Technical Design

According to the provided chapter notes, software design is an iterative, two-part process: conceptual design and technical design.

Conceptual Design

Explains to the customer what the system will do. It is expressed in simple, customer-understandable language.

  • Describes system characteristics and functionality.
  • Independent of implementation details.
  • Linked with the requirements document.
  • Helps the customer understand the proposed solution.

Technical Design

Explains to the system builders how the solution will be implemented.

  • Hardware components and design.
  • Functionality and hierarchy of software components.
  • Software and network architecture.
  • Data structures and data flow.
  • Input/output components and interfaces.

Conceptual design vs Technical design

Conceptual DesignTechnical Design
Customer-oriented description.Developer / system-builder-oriented description.
Explains what the system will do.Explains how the system will be built.
Uses simple, understandable language.Contains technical details and structures.
Independent of implementation.Considers hardware, software, data and interfaces.
Closely linked to requirements.Provides a blueprint for implementation.

04.3 Software Design Principles

Software design principles guide the organization and arrangement of structural components. The following principles are listed in the supplied chapter notes.

  1. Should not suffer from tunnel vision: Design should not focus only on achieving the immediate goal; it should also consider wider effects and constraints.
  2. Traceable to the analysis model: The design should be traceable to the analysis model and satisfy the requirements identified during analysis.
  3. Do not reinvent the wheel: Reuse existing solutions, components and proven approaches where appropriate instead of unnecessarily creating them again.
  4. Minimize intellectual distance: Reduce the gap between the real-world problem and the software solution so that the design reflects the problem domain clearly.
  5. Exhibit uniformity and integration: Maintain consistency across the design and ensure that the subsystems fit together as one system.
  6. Accommodate change: Structure the software so that changes can be made with minimum impact on other components.
  7. Degrade gently: The system should handle errors and abnormal conditions gracefully rather than failing unpredictably.
  8. Assess design quality: Evaluate the design against quality goals such as maintainability, reliability and understandability.
  9. Review to discover errors: Review the design to identify defects, omissions, inconsistencies and opportunities for improvement.
  10. Design is not coding, and coding is not design: Design defines the solution structure and logic; coding implements that design using a programming language.
Remember: Traceability, reuse, simplicity, consistency, changeability, graceful failure and review are recurring themes in good software design.

04.4 Design Process and Design Issues

Design is an iterative activity. A design is developed, examined, reviewed and refined until it provides a suitable solution to the requirements.

Conceptual overview of the design activity. The review loop represents iterative refinement.

Important design issues to consider

  • Requirements coverage: Every required function and constraint should be addressed by the design.
  • Modularity: The system should be divided into manageable components.
  • Interfaces: Interactions between components and with external systems should be clearly defined.
  • Data design: Data structures, storage and data movement should be specified.
  • Architecture: The high-level organization and relationships among components should be established.
  • Quality attributes: Performance, reliability, security, usability and maintainability should be considered where required.
  • Change and reuse: The design should support likely changes and appropriate reuse.

04.5 Modularization and Effective Modular Design

Modularization: The process of dividing a software system into multiple smaller modules, where each module performs a well-defined part of the overall system functionality.

A module is a separately identifiable part of a software system. Modules interact through defined interfaces and together provide the complete system behaviour.

Advantages of modularization

  • Understandability: Smaller parts are easier to understand than one large system.
  • Maintainability: Changes can often be limited to the affected module.
  • Reusability: A module may be reused in other programs requiring the same functionality.
  • Testing: Individual modules can be tested separately.
  • Team development: Different developers can work on different modules with clearly defined interfaces.
  • Error isolation: Defects can be easier to locate when responsibilities are separated.

Characteristics of effective modular design

  • Each module should have a clear and focused responsibility.
  • Modules should communicate through simple, well-defined interfaces.
  • Dependencies between modules should be minimized.
  • Internal details should be hidden where possible.
  • Modules should be independently understandable, testable and maintainable.
  • Changes inside one module should have limited impact on other modules.

04.6 Functional Independence

Functional Independence: A module is functionally independent when it focuses on a single task and performs that task with little or no unnecessary interaction with other modules.

Functional independence is achieved through high cohesion and low coupling.

Illustrative modular structure. Each module owns a focused responsibility and communicates through defined interfaces.

Example: Calculator application

A calculator can be divided into addition, subtraction, multiplication and division modules. Each module receives the required operands and performs its own operation. The addition module does not need to depend on the internal implementation of the subtraction or multiplication module.

Advantages of functional independence

  • Error isolation: Fewer dependencies reduce the chance of errors propagating across modules and make defects easier to trace.
  • Module reusability: A focused module can be reused wherever the same function is required.
  • Understandability: A module with a clear responsibility and few dependencies is easier to understand in isolation.
  • Maintainability: Changes to one module are less likely to require changes in unrelated modules.

04.7 Coupling

Coupling: The measure of the degree of interdependence between software modules. A good software design aims for low coupling.

Coupling describes how strongly one module depends on another. High coupling makes modules harder to change, reuse, test and maintain independently.

Types of coupling

TypeDescriptionExampleRelative quality
Data CouplingModules communicate by passing only the data required by the receiving module.A billing module receives a customer ID and amount from another module.Lowest / desirable among the listed types.
Stamp CouplingA complete data structure is passed between modules, although the receiving module may use only part of it.Passing an entire customer record when only the customer name is needed.More dependency than data coupling.
Control CouplingOne module passes control information that affects the logic or execution path of another module.Passing a flag that tells a function which operation to perform.Generally less desirable than data coupling.
External CouplingModules depend on externally imposed formats, protocols, devices or communication interfaces.Two modules depend on the same external file format or communication protocol.External dependency.
Common CouplingMultiple modules access shared global data or a common data structure.Several modules read and modify the same global variable.High dependency; difficult to control and maintain.
Content CouplingOne module directly accesses or modifies the internal data or logic of another module, or branches into its internal code.One module changes a local variable belonging to another module.Highest / worst form in this classification.
Coupling order (best to worst): Data → Stamp → Control → External → Common → Content.

Note: The examples above clarify the coupling categories described in the provided chapter notes. In practice, the exact degree of dependency depends on the interface and implementation.

04.8 Cohesion

Cohesion: The measure of how strongly the elements within a module are functionally related. It describes the internal unity of a module. A good software design aims for high cohesion.

High cohesion means that the elements of a module contribute to one well-defined responsibility. Low cohesion means that unrelated or weakly related activities are grouped together.

Types of cohesion

TypeDescriptionExampleRelative quality
Functional CohesionEvery element contributes to one specific computation or function.A module that calculates the final invoice total.Highest / ideal.
Sequential CohesionThe output of one part becomes the input of the next part.Read data → validate data → process validated data.Strong.
Communicational CohesionElements operate on the same input data or contribute to the same output data.Update a database record and produce an output based on that record.Moderately strong.
Procedural CohesionElements are grouped because they must follow a particular execution sequence, though they may perform different functions.Calculate GPA, print student record, calculate cumulative GPA, print cumulative GPA.Weaker.
Temporal CohesionElements are grouped because they are executed during the same time period.A startup module that performs several initialization tasks.Weak.
Logical CohesionElements perform logically similar categories of activities, and a control parameter selects which activity is executed.A module containing input operations for tape, disk and network.Very weak.
Coincidental CohesionUnrelated elements are placed in the same module without a meaningful functional relationship.A module that prints a line and reverses a string for no common purpose.Lowest / worst.
Cohesion order (best to worst): Functional → Sequential → Communicational → Procedural → Temporal → Logical → Coincidental.

04.9 Difference Between Coupling and Cohesion

CouplingCohesion
Measures dependency between different modules.Measures the relationship among elements within one module.
Focuses on inter-module relationships.Focuses on intra-module relationships.
Low coupling is desirable.High cohesion is desirable.
High coupling makes independent changes difficult.High cohesion gives a module a clear, focused responsibility.
Helps reduce dependency between modules.Helps keep related responsibilities together.
Most important exam line: Good modular design aims for high cohesion within each module and low coupling between modules.

04.10 Architectural Design

Software Architecture: The high-level organization of a software system, describing its major components, their responsibilities, their relationships and the way they interact.

Architectural design establishes the overall structure of the system before detailed component-level design and coding. It helps stakeholders understand the system organization and provides a basis for detailed design.

What architectural design identifies

  • Major software components or subsystems.
  • Responsibilities assigned to each component.
  • Connections and communication among components.
  • Data flow and control flow across the system.
  • External interfaces and integration points.
  • Important constraints and quality requirements that influence the structure.

Benefits of architectural design

  • Provides a high-level view of the complete system.
  • Helps divide a complex system into understandable subsystems.
  • Supports communication among developers and stakeholders.
  • Helps identify major design risks and constraints early.
  • Provides a framework for detailed design, implementation and testing.

04.11 Architectural Styles

Architectural style: A reusable way of organizing the components of a software system and defining how those components communicate and interact.

An architectural style provides a general structural pattern. Different styles are appropriate for different system requirements and constraints.

1. Data-Centered Architecture

A central data store is accessed and updated by multiple independent components.

Example: Several business applications using a shared central database.

2. Data-Flow Architecture

Data passes through a sequence of transformations. Each processing component receives input, transforms it and passes output onward.

Example: A compiler pipeline or batch data-processing system.

3. Call-and-Return Architecture

The system is organized as a hierarchy of modules. A main program calls subordinate modules, which may call other modules.

Example: A procedural application with a main routine and helper functions.

4. Object-Oriented Architecture

The system is organized as interacting objects that encapsulate state and behaviour. Objects collaborate through defined interfaces or messages.

Example: A library application with Member, Book and Loan objects.

5. Layered Architecture

The system is organized into layers. Each layer provides services to the layer above it and may use services from the layer below it.

Example: Presentation, business-logic and data-access layers in an application.
