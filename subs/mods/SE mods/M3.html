Software Estimation Metrics and Project Scheduling

This module covers the management spectrum, software metrics, size and function-oriented estimation, COCOMO II, and the planning and tracking techniques used to control a software project.

03.1 Management Spectrum – The 3 P’s

Definition: The management spectrum describes the key areas that must be managed to make a software project successful. It focuses on People, Product and Process.

1. People

People involved in a project range from the project manager and developers to customers and end users. Skilled and motivated people improve software development capability.

People Management Capability Maturity Model (PM-CMM): A framework developed by the Software Engineering Institute (SEI) to improve the maturity of an organisation's people-management practices.

2. Product

The product is the software to be designed and developed. Before estimating cost, effort and schedule, the team must understand the product objectives, scope, functions, constraints and performance requirements.

Insufficient product information makes reliable estimates difficult.

3. Process

The software process provides the framework for establishing a complete development plan. It identifies the activities and tasks required to build the product.

Process elements include tasks, milestones, work products and quality-assurance points. Umbrella activities support the process throughout the project.

Exam memory key: People = who builds it; Product = what is being built; Process = how it is built.

03.2 Software Metrics

Software metric: A quantitative measure of a software characteristic. Metrics help measure software products and processes, plan work, evaluate productivity, monitor quality and support project control.

Classification of software metrics

Product metrics

Measure characteristics of the software product, such as size, complexity, performance, reliability, defects and maintainability.

Process metrics

Measure the effectiveness of the software development process, such as defect removal efficiency, review effectiveness, cycle time and rework.

Project metrics are used by a project manager to monitor project status, effort, cost, schedule, staffing and risks. They support day-to-day project decisions.

Size-oriented metrics

Size-oriented metrics are derived by considering the amount of software produced, commonly measured in Lines of Code (LOC) or Thousand Lines of Code (KLOC).

KLOC = LOC / 1000

Common derived measures include:

MetricFormulaInterpretation
ProductivityLOC / Person-monthSoftware size produced per unit of effort.
Quality (defects)Defects / KLOCDefect density by software size.
CostProject cost / LOC (or KLOC)Cost per unit of software size.
DocumentationPages of documentation / KLOCDocumentation produced relative to size.
Note: LOC-based comparisons can be misleading across programming languages and development styles. LOC is also difficult to estimate accurately early in a project.

03.3 LOC and Function Point Estimation

A. LOC-based estimation

LOC estimation predicts software size by estimating the number of source-code lines required. The estimate is often expressed in KLOC and then used with historical productivity and cost data to estimate effort and cost.

Estimated effort (person-months) = Estimated LOC / Historical LOC productivity per person-month

Example: If the estimated size is 24,000 LOC and historical productivity is 600 LOC per person-month:

Effort = 24,000 / 600 = 40 person-months

B. Function Point (FP) estimation

Function Point: A measure of the functionality delivered by a software system. Function points estimate software size from the user's view, rather than depending directly on the programming language or number of code lines. The function-oriented metric concept was initially proposed by Allan Albrecht.

Five information-domain characteristics are counted and classified by complexity:

CharacteristicMeaningTypical example
External Inputs (EI)Data entering the system and updating internal data.Registration form, login input.
External Outputs (EO)Information produced and sent outside the system.Reports, formatted screens, error messages.
External Inquiries (EQ)Online input that results in an immediate online response.Search or lookup request.
Internal Logical Files (ILF)Logical groups of data maintained by the application.Student database maintained by the system.
External Interface Files (EIF)Logical groups of data used by the application but maintained externally.University database accessed by the system.

Standard function point weighting factors

Measurement parameterSimpleAverageComplex
External Inputs346

Function Point calculation

UFP (Unadjusted Function Points) = Σ (Count × Weight)

The complexity adjustment factor is calculated using 14 general system characteristics (GSCs), each rated for its degree of influence.

CAF = 0.65 + 0.01 × Σ(Fᵢ), where i = 1 to 14
AFP (Adjusted Function Points) = UFP × CAF

Here, Fᵢ is the influence rating for each of the 14 characteristics; the sum is the Total Degree of Influence (TDI). The base adjustment factor is 0.65 and the adjustment multiplier is 0.01.

Fourteen general system characteristics

  1. Data communications
  2. Distributed data or functions
  3. Performance objectives
  4. Heavily used configuration
  5. High transaction rate
  6. Online data entry
  7. End-user efficiency
  8. Online updates
  9. Complex processing
  10. Reusability for other applications
  11. Installation and conversion ease
  12. Operational ease
  13. Multiple-site access
  14. Facilitation of change

Solved example – Function Points

Consider a system with the following counts and complexity levels:

Function typeCountComplexityWeightSubtotal
External Inputs3Average43 × 4 = 12
External Outputs2Average52 × 5 = 10
External Inquiries2Average42 × 4 = 8
Internal Logical Files2Average102 × 10 = 20
External Interface Files1Average71 × 7 = 7

Suppose the sum of the 14 influence ratings is 35.

CAF = 0.65 + (0.01 × 35) = 1.00
AFP = 57 × 1.00 = 57 Function Points

If the cost per function point is ₹4,000:

Estimated development cost = 57 × ₹4,000 = ₹2,28,000
Calculation order: Count each function → select its complexity weight → calculate UFP → add the 14 influence ratings → calculate CAF → calculate AFP → multiply by cost per FP if required.

03.4 Software Project Estimation

Software project estimation: The process of predicting the resources, effort, cost, size and time required to develop and deliver a software project.

What is estimated?

  • Size: LOC, KLOC or Function Points.
  • Effort: person-hours or person-months.
  • Cost: labour, tools, infrastructure and other project expenses.
  • Schedule: project duration and milestone dates.
  • Resources: people, skills, hardware and software tools.

General estimation workflow

  1. Define the project scope and objectives.
  2. Decompose the product and work into manageable components.
  3. Estimate software size using LOC, FP or another suitable measure.
  4. Estimate effort using historical data, productivity or an empirical model.
  5. Derive cost and schedule, accounting for risks and constraints.
  6. Compare estimates with actual project data and revise as details improve.

Common estimation techniques

TechniqueExplanationLimitation / consideration
Expert judgementExperienced professionals estimate based on similar work and domain knowledge.May be affected by bias or limited experience.
Estimation by analogyCompares the proposed project with completed, similar projects.Requires relevant historical projects.
DecompositionBreaks the project into smaller components and estimates each part.Small estimates must be combined consistently.
Empirical modelsUse mathematical relationships derived from historical project data.Accuracy depends on calibration and input quality.
Agile estimationUses relative sizing, story points, velocity and iteration planning.Velocity is team-specific and should not be treated as a universal rate.

03.5 COCOMO II Model

COCOMO II: The Constructive Cost Model II is an empirical software cost-estimation model used to estimate effort, schedule and related project resources from software size and cost drivers.

COCOMO II supports estimation at different stages of development. Its estimates depend on the chosen model, size measure, scale factors and effort multipliers. The model should be calibrated using relevant organisational data where possible.

COCOMO II sub-models

Sub-modelWhen usedPurpose
Application CompositionDuring prototyping or early user-interface/application composition.Uses object points such as screens, reports and 3GL components.
Early DesignWhen requirements and architecture are understood at a high level.Uses a small set of scale factors and effort multipliers.
Post-ArchitectureAfter the software architecture is defined.Uses more detailed cost drivers and project information.

Post-Architecture effort equation

Effort = A × (Size)E × ∏ EMᵢ

Where:

  • Effort: estimated person-months.
  • A: calibration constant (commonly 2.94 in the standard COCOMO II formulation).
  • Size: estimated software size in KSLOC, after accounting for reuse where applicable.
  • E: scale exponent determined by scale factors.
  • EMᵢ: effort multipliers representing cost-driver effects.
E = B + 0.01 × Σ(SFⱼ)

The standard COCOMO II formulation commonly uses B = 0.91. Scale factors include precedentedness, development flexibility, architecture/risk resolution, team cohesion and process maturity.

Schedule equation

TDEV = C × (Effort)F
F = D + 0.2 × (E − B)

In the standard formulation, C = 3.67 and D = 0.28. TDEV is development time in months. These constants belong to the standard model; use the values specified by the prescribed textbook or question if a different calibration is supplied.

Effort multipliers / cost drivers

Effort multipliers adjust the nominal effort to reflect product, platform, personnel and project characteristics. Examples include required reliability, database size, product complexity, execution-time constraints, analyst capability, programmer capability, personnel continuity, tool support and multisite development.

Important: Do not confuse scale factors with effort multipliers. Scale factors determine the exponent E; effort multipliers are multiplied together to adjust effort.

03.6 Specialized and Agile Estimation

Specialized estimation techniques

  • Expert judgement: an expert analyses the project and estimates size, effort or schedule from experience.
  • Delphi / Wideband Delphi: multiple experts estimate independently, discuss differences and repeat estimation rounds until a reasonable consensus is reached.
  • Estimation by analogy: uses actual data from similar completed projects and adjusts for differences.
  • Parkinson's Law: effort is estimated in relation to available resources and time; it is not a reliable substitute for a realistic effort estimate.
  • Price-to-win: estimate is constrained by the price needed to win a contract; this can create delivery risk if the price is below realistic cost.

Agile estimation

Agile teams commonly estimate relative effort rather than exact hours at the beginning of a project.

Story points

A relative measure of the effort, complexity and uncertainty of a user story. A point value is meaningful within the team, not as a universal time unit.

Velocity

The amount of story-point work completed by a team in an iteration. Historical velocity helps forecast future iteration capacity.

Estimated iterations ≈ Total remaining story points / Average team velocity

Example: If 120 story points remain and the team's average velocity is 30 points per sprint, the rough forecast is 120 / 30 = 4 sprints. This assumes similar team capacity and work conditions.

03.7 Project Scheduling

Project scheduling: The activity of defining the work to be performed, identifying task dependencies, assigning resources and estimating start and finish dates to create a roadmap for completing the project.

Objectives

  • Divide the project into manageable activities.
  • Identify task dependencies and sequencing.
  • Allocate people and other resources.
  • Estimate task duration and project completion time.
  • Identify milestones and monitor progress.
  • Detect schedule risks and take corrective action.

Scheduling principles

  1. Compartmentalisation: divide the project into manageable tasks.
  2. Interdependency: identify relationships and dependencies among tasks.
  3. Time allocation: assign realistic start dates, finish dates and durations.
  4. Effort validation: ensure that assigned effort and available resources are realistic.
  5. Defined responsibilities: assign responsibility for each task.
  6. Defined outcomes: specify deliverables or work products.
  7. Defined milestones: identify review points to assess progress.

03.8 Work Breakdown Structure and Task Set Definition

Work Breakdown Structure (WBS): A hierarchical decomposition of the project into smaller deliverables and work packages that can be estimated, assigned and monitored.

A WBS starts with the complete project and progressively divides it into phases, deliverables, activities and work packages.

Illustrative WBS. Actual work packages should be decomposed until they can be estimated and assigned clearly.

Task set definition

A task set is the collection of software engineering tasks, milestones and deliverables required for a particular project. The task set is selected according to project size, complexity, risk, process model and required quality.

Each task should have:

  • A clear description and expected outcome.
  • Estimated effort and duration.
  • Predecessors and dependencies.
  • An assigned owner or responsible role.
  • Required resources and deliverables.
  • Completion criteria or milestone.

03.9 Timeline Charts and Gantt Chart

A timeline chart represents project tasks against calendar time. A Gantt chart is a bar chart in which each task is represented by a horizontal bar positioned according to its planned start and finish dates.

Example Gantt schedule

Requirements■■
Design◆■
Implementation■■■
Testing■■
Release◆

■ = planned work period; ◆ = milestone. This is an illustrative schedule, not a fixed project duration.

Advantages

  • Easy to understand and communicate.
  • Shows task durations, overlaps and milestones.
  • Helps compare planned progress with actual progress.
  • Highlights tasks that are delayed.

Limitations

  • Large projects can produce crowded charts.
  • Complex dependencies may be difficult to understand from bars alone.
  • A Gantt chart does not by itself identify the critical path unless dependencies and critical tasks are also analysed.

03.10 Critical Path Method and PERT

A. Critical Path Method (CPM)

Critical Path Method: A network-based scheduling technique that determines the longest-duration path through a project network. The critical path establishes the minimum project completion time when the task durations and dependencies are fixed.

Activities on the critical path have zero total float under the calculated schedule. A delay in a critical activity delays the project unless corrective action is taken.

CPM terms and formulas

TermMeaning
ESEarliest Start time.
EFEarliest Finish time = ES + Duration.
LSLatest Start time without delaying project completion.
LFLatest Finish time without delaying project completion.
Float / SlackTime an activity can be delayed without delaying project completion (total float).
EF = ES + Duration
LS = LF − Duration
Total Float = LS − ES = LF − EF

CPM calculation procedure

  1. List all activities, durations and immediate predecessors.
  2. Draw the activity network according to dependencies.
  3. Perform the forward pass to calculate ES and EF.
  4. Perform the backward pass to calculate LS and LF.
  5. Calculate float for every activity.
  6. Identify the path with the longest total duration and zero-float activities.

Illustrative CPM network

Conceptual network only. For a numerical CPM problem, use the exact activity table and dependencies supplied in the question.

B. Program Evaluation and Review Technique (PERT)

PERT: A probabilistic network scheduling technique used when activity durations are uncertain. It uses three time estimates to calculate an expected activity duration.
EstimateSymbolMeaning
OptimisticOShortest reasonable duration under favourable conditions.
Most likelyMDuration expected under normal conditions.
PessimisticPLongest reasonable duration under unfavourable conditions.
Expected time (TE) = (O + 4M + P) / 6
Variance = ((P − O) / 6)²
Standard deviation = (P − O) / 6

Solved example: An activity has O = 2 days, M = 5 days and P = 8 days.

TE = (2 + 4(5) + 8) / 6 = 30 / 6 = 5 days
Variance = ((8 − 2) / 6)² = 1 day²
Standard deviation = 1 day

CPM vs PERT

CPMPERT
Uses a single activity-duration estimate in its basic form.Uses optimistic, most likely and pessimistic estimates.
Suitable when durations are reasonably predictable.Useful when activity durations are uncertain.
Emphasises critical path and float.Emphasises expected duration and schedule uncertainty.
Deterministic scheduling technique.Probabilistic scheduling technique.

03.11 Schedule Tracking and Earned Value Analysis

Schedule tracking

Schedule tracking compares actual project progress with the approved schedule. It helps identify slippage early and supports corrective action.

  • Review completed tasks and milestone status regularly.
  • Compare actual start and finish dates with planned dates.
  • Update task estimates and dependencies when justified.
  • Identify critical activities that are delayed.
  • Reallocate resources or revise the plan when necessary.
  • Communicate schedule changes to stakeholders.

Earned Value Analysis (EVA)

Earned Value Analysis: A project-control technique that integrates scope, schedule and cost to measure project performance against a baseline.
TermMeaning
PV – Planned ValueBudgeted value of work scheduled to be completed by the status date.
EV – Earned ValueBudgeted value of the work actually completed by the status date.
AC – Actual CostActual cost incurred for the work completed by the status date.
BAC – Budget at CompletionTotal approved budget for the project.

Important EVA formulas

Schedule Variance (SV) = EV − PV
Cost Variance (CV) = EV − AC
Schedule Performance Index (SPI) = EV / PV
Cost Performance Index (CPI) = EV / AC
  • SV > 0: ahead of planned schedule in earned-value terms; SV < 0: behind schedule.
  • CV > 0: under budget for the work performed; CV < 0: over budget.
  • SPI > 1: schedule performance is better than planned; SPI < 1: behind plan.
  • CPI > 1: cost efficiency is better than planned; CPI < 1: cost efficiency is worse than planned.

Solved EVA example

At the status date, a project has PV = ₹50,000, EV = ₹40,000 and AC = ₹45,000.

SV = EV − PV = 40,000 − 50,000 = −₹10,000
CV = EV − AC = 40,000 − 45,000 = −₹5,000
SPI = EV / PV = 40,000 / 50,000 = 0.80
CPI = EV / AC = 40,000 / 45,000 ≈ 0.89

Interpretation: The project is behind schedule because SPI is below 1 and has an unfavourable cost position because CPI is below 1. It has earned ₹0.80 of planned value for each ₹1 of planned work and ₹0.89 of earned value for each ₹1 spent.
