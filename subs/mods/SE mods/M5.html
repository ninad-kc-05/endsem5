Software Engineering · Module 05

Software Testing

Software testing checks whether actual software behaviour agrees with expected results and whether the developed product satisfies its requirements. This module follows the supplied Unit 5 notes and question-bank coverage: testing levels and strategies, white-box testing, black-box testing, basis paths, cyclomatic complexity, equivalence partitioning and boundary value analysis.

05.1 Software Testing Fundamentals

Software Testing: A procedure used to verify whether the actual results of a software product are the same as the expected results. Testing provides assurance that the software does not contain defects and checks whether the required features are present.

To perform software testing, test cases and test data are prepared and executed against the software.

Test Case

A collection of actions or steps applied to a software product to check a specific feature or functionality. A test case normally specifies the input, execution conditions and expected result.

Test Data

The input values supplied to a module or software under test so that its behaviour can be checked.

Advantages of software testing

  1. Reduces the possibility of software failure by helping detect and remove errors.
  2. Helps deliver a qualitative software product to the customer.
  3. Checks the correctness and completeness of the software product.
  4. Checks whether the software satisfies user requirements.
  5. Helps ensure that the software produces the expected outcome.
Important distinction: Testing can reveal the presence of defects; passing tests do not mathematically prove that a program is completely defect-free.

05.3 Unit Testing

Unit Testing: A testing technique in which individual software modules are tested independently to identify issues. It checks the functional correctness of standalone modules.

The main aim is to isolate each unit of the system so that defects can be identified, analysed and fixed. The supplied notes state that unit testing is generally performed by the developer.

Unit testing techniques mentioned in the notes

Black-Box Testing

Checks the module through its inputs and outputs without relying on knowledge of its internal code.

White-Box Testing

Examines internal program structure and logic, including statements, branches and paths.

Gray-Box Testing

Uses partial knowledge of internal design or implementation while testing the software behaviour.

Example

Login validation unit: Test the login-validation function separately. Supply a valid username and password, an incorrect password, an empty username and an empty password. Compare each actual result with the expected result.

05.4 Integration Testing

Integration Testing: Testing performed after individual modules have been unit-tested, to check whether the combined modules and their interfaces work correctly together.

Integration testing is necessary because individually working modules may still fail when connected. The supplied notes identify these reasons:

  • Requirements may change during module development, and new requirements may not have been covered by unit testing.
  • Interfaces between software modules and the database may contain errors.
  • External hardware interfaces, if present, may be erroneous.
  • Inadequate exception handling may cause problems when modules interact.
Focus of integration testing: Interfaces, communication, data transfer and interaction between combined modules.

05.5 Integration Testing Approaches

The notes divide integration testing into Big Bang and Incremental approaches. Incremental integration includes Top-Down, Bottom-Up and Sandwich approaches.

A. Big Bang Integration Testing

Big Bang Testing: All completed components or modules are integrated at once and then tested as one combined entity. Integration cannot proceed until all required modules are ready.

Advantages

  • Convenient for small systems.

Disadvantages

  • Fault localization is difficult because many modules are combined at once.
  • Some interfaces may be missed during testing.
  • Testing starts late because all modules must be ready first, leaving less execution time.
  • High-risk modules are not isolated and tested on priority.

B. Top-Down Integration Testing

Top-Down Testing: Integration starts with higher-level modules and proceeds downwards, following the system's control flow. Lower-level modules that are not yet available are represented by stubs.

Conceptual top-down structure: stubs stand in for lower-level modules that have not yet been integrated.

Advantages

  • Fault localization is comparatively easier.
  • An early working prototype can be obtained.
  • Critical high-level modules are tested first, so major design flaws may be found early.

Disadvantages

  • Many stubs may be required.
  • Lower-level modules may receive inadequate testing early in the process.

C. Bottom-Up Integration Testing

Bottom-Up Testing: Integration begins with lower-level modules. Tested lower-level modules are combined to form higher-level groups, and the process continues until the top-level modules have been integrated.

Conceptual bottom-up structure: lower-level modules are combined and tested before higher-level integration.

Bottom-up testing commonly uses drivers to call lower-level modules when the higher-level calling modules are not yet available. The provided notes explain the order of integration but do not list a separate advantages/disadvantages table for this approach.

D. Sandwich (Hybrid) Integration Testing

Sandwich Testing: A hybrid strategy combining Top-Down and Bottom-Up integration. Top-level modules are integrated downwards while lower-level modules are integrated upwards. It uses both stubs and drivers.

The two integration directions meet around the middle layer; the strategy uses stubs and drivers.

Comparison of integration approaches

ApproachIntegration orderTemporary supportKey point

05.6 Validation Testing and System Testing

Validation Testing

Validation Testing: Testing performed to evaluate whether the developed software satisfies the specified requirements and meets the user's needs.

Validation focuses on whether the right product has been built. It checks the software against the requirements and expected use.

System Testing

System Testing: Testing of the entire, completely integrated software product. It is end-to-end testing of the system as a whole.

Example from the supplied notes: a college admission system may be tested through the complete sequence of Login → Enquiry → Admission → Logout.

Example end-to-end flow for system testing, based on the college admission example in the notes.

System testing includes both functional and non-functional testing.

05.8 Black-Box and White-Box Testing

Black-Box Testing

Tests software functionality by supplying inputs and checking outputs without examining the internal program structure. It focuses on externally observable behaviour.

Techniques in the notes: Graph-Based Testing, Equivalence Class Partitioning and Boundary Value Analysis.

White-Box Testing

Tests the internal structure and logic of the program. Test cases are designed with knowledge of statements, decisions, conditions, paths, loops and data flow.

Techniques in the notes: Basis Path Testing and Control Structure Testing.

Difference between Black-Box and White-Box Testing

Black-Box TestingWhite-Box Testing
Tests externally visible functionality.Tests internal code structure and logic.
Does not require knowledge of source code.Requires knowledge of internal implementation or design.
Test cases are derived from requirements, input domains and expected outputs.Test cases are derived from statements, branches, paths, conditions and data flow.
Examples: equivalence partitioning, boundary value analysis and graph-based testing.Examples: basis path, condition, loop and data-flow testing.

05.9 Basis Path Testing

Basis Path Testing: A white-box testing technique proposed by Tom McCabe. It uses a program's control-flow graph to identify a set of linearly independent execution paths and design test cases that exercise those paths.

The supplied notes describe a basis path as a set of execution paths of a procedure. The goal is to derive test cases that force execution of the basis set and check that each path reaches the procedure's endpoint as expected.

Flow graph terminology

  • Node: Represents one or more procedural statements. A node containing a condition is called a predicate node.
  • Edge: Represents the flow of control from one node to another.
  • Region: An area bounded by nodes and edges in the flow graph; the outside area is also counted as a region.
  • Predicate node: A decision node that contains a condition and has alternative outgoing paths.
  • Independent path: A path that introduces at least one new edge not included in the previously selected paths.

Example control-flow graph

Illustrative flow graph for understanding nodes, edges and independent routes. It is not the same numerical graph as the 13-node, 17-edge worked example reported in the notes.

Steps in Basis Path Testing

  1. Derive a control-flow graph from the program design or source code.
  2. Calculate the cyclomatic complexity V(G) of the flow graph using any valid formula.
  3. Identify a basis set containing V(G) linearly independent paths.
  4. Prepare test cases that force execution of each selected path.
  5. Execute each test case and compare actual results with expected results.

05.10 Cyclomatic Complexity

Cyclomatic Complexity: A software metric introduced by Thomas McCabe that measures the number of linearly independent paths in a program's control-flow graph. It indicates the minimum number of independent path tests needed for basis path testing.

Three ways to calculate cyclomatic complexity

V(G) = E − N + 2P For a single connected component: V(G) = E − N + 2 V(G) = Pn + 1 V(G) = Number of regions
  • E = number of edges in the flow graph.
  • N = number of nodes in the flow graph.
  • P = number of connected components (for a single program flow graph, P = 1).
  • Pn = number of predicate/decision nodes in the flow graph.

Worked example from the supplied notes

The notes provide a flow graph with E = 17 edges, N = 13 nodes and 5 predicate nodes.

Method 1: V(G) = E − N + 2 = 17 − 13 + 2 = 6 Method 2: V(G) = Pn + 1 = 5 + 1 = 6 Method 3: Number of regions = 6 Therefore, Cyclomatic Complexity V(G) = 6.

Thus, six linearly independent paths are required in the basis set for that example. The notes list these four path sequences from the flow graph:

1. 1 – 2 – 3 – 5 – 8 – 11 – 13 2. 1 – 2 – 4 – 5 – 7 – 11 – 13 3. 1 – 2 – 4 – 6 – 10 – 12 – 13 4. 1 – 2 – 4 – 6 – 9 – 12 – 13
Source limitation: The extracted notes show four path sequences but state that V(G) = 6. The remaining two path sequences are not visible in the available text, so they are not invented here.

05.11 Control Structure Testing

The supplied notes identify three white-box control-structure techniques: Condition Testing, Loop Testing and Data Flow Testing.

A. Condition Testing

Condition Testing: A white-box testing technique that checks Boolean conditions in a program. Condition coverage (also called predicate coverage in the notes) requires each Boolean condition to evaluate to both TRUE and FALSE at least once.

Example condition from the notes:

if ((A || B) && C) { // statements } else { // other statements }

For the individual conditions A, B and C, the notes give these test assignments to exercise TRUE and FALSE outcomes, taking short-circuit evaluation into account:

TestABCPurpose / evaluation note
1TRUENot evaluatedFALSEA is TRUE; C is FALSE.
2FALSETRUETRUEA is FALSE; B and C are TRUE.
3FALSEFALSENot evaluatedA and B are FALSE; short-circuit evaluation means C is not evaluated.

Exam caution: “Not evaluated” is not the same as evaluating a condition to FALSE. Explain the chosen coverage criterion and short-circuit behaviour when solving such questions.

B. Loop Testing

Loop Testing: A white-box testing technique that focuses on the validity of loop construction and the behaviour of loops under different iteration conditions.

The notes list these loop structures:

  • Simple loop: A single loop with no other loop nested inside it.
  • Concatenated loops: Two or more loops placed one after another.
  • Unstructured loops: Complex loop arrangements that do not follow a simple structured pattern.
Example: For a loop that processes a list, test the case where the list is empty, contains one item, contains several items and reaches the maximum supported size. Also test termination and off-by-one behaviour.

C. Data Flow Testing

Data Flow Testing: A white-box technique that selects test paths based on where variables are defined, used and potentially left without a valid definition.

It examines the lifecycle of data through the program, such as variable definition, computation, use and the paths connecting those operations. The supplied notes list Data Flow Testing as a control-structure technique but do not provide a worked example or detailed criteria.

05.12 Black-Box Testing: Equivalence Class Partitioning

Equivalence Class Partitioning (ECP): A black-box testing technique in which the input domain is divided into groups (equivalence classes) whose values are expected to be processed similarly. One or more representative values are selected from each class to reduce the number of test cases.

The technique is useful when an input field accepts a defined range of values. Both valid and invalid input classes should be considered.

Worked example: Password length

Suppose a password field accepts a minimum of 6 characters and a maximum of 10 characters. The notes divide the input into these classes:

Equivalence classInput rangeClass statusRepresentative test valueExpected result
EC10–5 charactersInvalid4 charactersReject password.
EC26–10 charactersValid8 charactersAccept password, subject to other rules.
EC311–14 characters (as shown in notes)Invalid12 charactersReject password.

The upper invalid range is shown as 11–14 in the supplied example. In a real specification, the invalid class should cover all values greater than 10, not stop at 14.

Steps

  1. Identify the input condition and its valid range.
  2. Divide the domain into valid and invalid equivalence classes.
  3. Select representative values from each class.
  4. Prepare test cases and compare actual outcomes with expected outcomes.

05.13 Black-Box Testing: Boundary Value Analysis

Boundary Value Analysis (BVA): A black-box testing technique that selects test inputs at the boundaries of an input range because defects frequently occur at minimum and maximum limits or immediately around them.

The normal boundary value selection described in the notes uses five values for an input variable:

  1. Minimum value.
  2. Just above the minimum.
  3. A nominal (typical) value.
  4. Just below the maximum.
  5. Maximum value.

Worked example: Pizza order quantity

Suppose a pizza-order text box accepts values from 1 to 10. Values from 1 through 10 are valid; values above 10 are invalid and should display the message: “Only 10 Pizza can be ordered”.

Test positionInputExpected result
Minimum1Valid order.
Just above minimum2Valid order.
Nominal value5Valid order.
Just below maximum9Valid order.
Maximum10Valid order.

For robust boundary checking, also test values immediately outside the valid range:

Outside boundaryInputExpected result
Just below minimum0Reject input.
Just above maximum11Reject input and show the specified error message.
Difference to remember: ECP selects representative values from input classes; BVA deliberately selects values at and around the limits of those classes.

05.14 Black-Box Testing: Graph-Based Testing

Graph-Based Testing: A black-box testing technique, also called State-Based Testing in the supplied notes, that represents relationships between system behaviour and the factors that affect its output using a graph.

The notes emphasize that this technique explains the relationship between system outputs and the factors affecting them, and tests the behaviour of the system.

Simple state-based example — order status: An order may move from Placed to Paid, then to Dispatched and finally to Delivered. A graph can represent these states and valid transitions. Tests can check that valid transitions occur and invalid transitions are rejected.
