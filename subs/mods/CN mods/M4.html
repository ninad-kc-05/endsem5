1. Transport Layer: Role and Services

Definition

The Transport Layer is Layer 4 of the OSI reference model. It provides logical communication between application processes running on different hosts. While the Network Layer delivers packets from one host to another, the Transport Layer delivers data to the correct process or application within the destination host.

Important functions

  1. Process-to-process delivery: Uses port numbers to identify sending and receiving application processes.
  2. Segmentation and reassembly: Divides application data into transport segments and reassembles received data at the destination.
  3. Multiplexing and demultiplexing: Allows multiple applications to use the network simultaneously and delivers incoming data to the correct application.
  4. Connection control: Supports connection-oriented communication (TCP) or connectionless communication (UDP).
  5. Flow control: Prevents a fast sender from overwhelming a slower receiver.
  6. Error control / reliability: TCP detects loss and corruption and uses acknowledgements and retransmissions to provide reliable, ordered delivery.
  7. Congestion control: TCP adjusts its sending rate according to network congestion conditions.

Port numbers identify application endpoints at the transport layer.

Transport Layer and Network Layer

Network Layer Transport Layer
Provides host-to-host delivery. Provides process-to-process delivery.
Uses logical IP addresses. Uses port numbers along with IP addresses.
Routers primarily process this layer's packets. End hosts process transport segments.
IP offers connectionless, best-effort delivery. TCP adds reliable connection-oriented service; UDP offers connectionless datagram service.

2. Transport Service Primitives

A service primitive is an operation provided by a layer to the layer above it. Transport service primitives describe how an application requests transport communication. The exact API varies by operating system and transport implementation; the following are the classic connection-oriented service operations.

Primitive Purpose Typical role
LISTEN Waits for an incoming connection request. Server prepares to accept a client.
CONNECT Actively attempts to establish a connection with a remote endpoint. Client initiates a connection.
ACCEPT Accepts an incoming connection request and creates/returns a connection endpoint. Server accepts a client.
SEND Transfers data over an established connection. Either endpoint sends data.
RECEIVE Waits for and obtains incoming data. Either endpoint receives data.
DISCONNECT Releases or closes the transport connection. Either endpoint initiates connection release.

Typical server and client sequence

Exam point: LISTEN and ACCEPT are generally associated with a passive server; CONNECT is generally used by the active client. SEND and RECEIVE exchange data after connection establishment.

3. Berkeley Sockets and Socket Programming

What is a socket?

A socket is an endpoint used by an application to communicate over a network. The Berkeley sockets API provides programming calls for creating and using sockets. A socket is commonly identified by a combination of an IP address, a transport protocol and a port number. For a TCP connection, the two endpoints together identify the connection.

Common Berkeley socket calls

Call Purpose
socket() Creates a socket endpoint and selects the address family and socket type.
bind() Associates a local IP address and port with a socket.
listen() Marks a stream socket as passive and specifies a connection-request queue limit.
accept() Accepts a pending connection and returns a new connected socket.
connect() Initiates a connection to a remote socket address.
send() / recv() Send and receive data on a connected socket.
sendto() / recvfrom() Send and receive datagrams, commonly used with UDP.
close() Closes a socket descriptor and releases its local resources.

TCP client-server socket sequence

UDP socket sequence

A UDP application commonly creates a datagram socket with socket(), optionally uses bind() to select a local port, sends datagrams using sendto(), receives them using recvfrom(), and closes the socket using close(). There is no TCP-style connection handshake in basic UDP communication.

Self-learning focus: Be able to explain the purpose and order of socket calls. A complete socket-programming implementation also requires address structures, error checking, byte-order conversion and correct resource cleanup; these are beyond the detail explicitly listed in the syllabus.

4. TCP Characteristics and Services

Transmission Control Protocol (TCP) is a connection-oriented, reliable, byte-stream transport protocol. It is designed to provide ordered delivery of data between application processes.

Main characteristics

  1. Connection-oriented: A logical connection is established before application data is exchanged and released after communication.
  2. Reliable delivery: Uses sequence numbers, acknowledgements, checksums and retransmissions to recover from loss or corruption.
  3. Byte-stream service: Applications write and read a continuous stream of bytes; TCP does not preserve application write boundaries as message boundaries.
  4. Full-duplex communication: Both endpoints can send and receive data simultaneously.
  5. Ordered delivery: Data is delivered to the receiving application in sequence.
  6. Flow control: A receiver advertises how much additional data it can accept.
  7. Congestion control: The sender regulates transmission according to perceived network congestion.
  8. Multiplexing: Port numbers allow multiple application connections to share a host's network interface.

Common TCP applications

TCP is commonly used by applications that need reliable, ordered byte delivery, including web traffic using HTTP/1.1 or HTTP/2 over TCP, file transfer, email transfer and remote terminal sessions. Modern HTTP/3 uses QUIC over UDP, so not all HTTP traffic uses TCP.

5. TCP Segment Header Structure

A TCP segment consists of a header followed by application data. The TCP header is at least 20 bytes and can be larger when options are present. The Data Offset field specifies the header length in 32-bit words.

Conceptual field layout. The first two 32-bit rows are subdivided to show the common field groups; the exact control-bit layout is described below.

TCP header fields

Field Size Function
Source Port 16 bits Identifies the sending application endpoint.
Destination Port 16 bits Identifies the receiving application endpoint.
Sequence Number 32 bits Identifies the sequence number of the first data byte in the segment (with special interpretation for SYN).
Acknowledgment Number 32 bits When ACK is set, indicates the next sequence number expected by the sender of the ACK.
Data Offset 4 bits Specifies TCP header length in 32-bit words.
Reserved Reserved bits Reserved for future use and normally set as specified by the protocol.
Control Flags 9 bits in the commonly shown modern header Includes NS, CWR, ECE, URG, ACK, PSH, RST, SYN and FIN.
Window Size 16 bits Advertises the receiver's available receive window (with window scaling negotiated when used).
Checksum 16 bits Error-detection checksum covering the TCP header and data, plus the IP pseudo-header.
Urgent Pointer 16 bits Indicates the urgent-data boundary when URG is set.
Options + Padding Variable May carry negotiated parameters such as MSS, window scale, SACK permitted, timestamps; padding aligns the header.
Data Variable Application byte stream carried by the segment.

Important TCP flags

  • SYN: Synchronizes sequence numbers and is used to establish a connection.
  • ACK: Indicates that the acknowledgment field is valid.
  • FIN: Indicates that the sender has finished sending data and wants to close its sending direction.
  • RST: Resets or aborts a connection.
  • PSH: Requests prompt delivery of data to the receiving application.
  • URG: Indicates that the urgent pointer field is significant.
  • ECE and CWR: Used in Explicit Congestion Notification (ECN) signalling.
Exam facts: Minimum TCP header = 20 bytes; maximum header = 60 bytes. TCP sequence and acknowledgment numbers count bytes, not segments.

6. TCP Connection Management: Three-Way Handshake

Before data transfer, TCP establishes a connection using a three-way handshake. The exchange synchronizes the initial sequence numbers of both endpoints and confirms that both sides can send and receive.

Steps

  1. SYN: The client sends a segment with SYN = 1 and an initial sequence number, for example SEQ = x.
  2. SYN + ACK: The server responds with SYN = 1 and ACK = 1, its own initial sequence number SEQ = y, and acknowledgment ACK = x + 1.
  3. ACK: The client sends ACK = 1 with SEQ = x + 1 and ACK = y + 1. The connection is established.

Why three messages?

  • The first message informs the server that the client wants to establish a connection and provides the client's initial sequence number.
  • The second message acknowledges the client's request and provides the server's initial sequence number.
  • The third message acknowledges the server's sequence number, confirming that the client received it.
Remember: SYN consumes one sequence number. Therefore, the acknowledgment for a SYN with sequence number x is x + 1, even if no application data is carried.

7. TCP Connection Termination

TCP is full duplex, so each direction is closed independently. A common orderly close uses four segments, although acknowledgments and FINs may sometimes be combined.

  1. Endpoint A sends FIN to indicate that it has no more data to send.
  2. Endpoint B acknowledges the FIN.
  3. When B has finished sending, it sends its own FIN.
  4. Endpoint A acknowledges the FIN. The active closer typically enters TIME-WAIT before fully releasing the connection.

TIME-WAIT

The endpoint performing the active close normally remains in TIME-WAIT for a period (commonly described as twice the maximum segment lifetime, 2MSL). This helps ensure that the final ACK can be retransmitted if necessary and that delayed segments from the old connection expire before the same connection identifiers are reused.

8. TCP Timers

TCP uses timers to detect missing acknowledgments, support retransmission and manage connection state. Timer details are important for reliable communication.

Timer Purpose
Retransmission timer Starts when data is sent. If the acknowledgment does not arrive before timeout, TCP retransmits the segment. The retransmission timeout (RTO) is calculated dynamically using measured round-trip time and variation.
Persist timer Prevents deadlock when a receiver advertises a zero window and a later window-update message may be lost. TCP periodically probes the receiver.
Keepalive timer Can be used to probe an otherwise idle connection to determine whether the peer is still reachable. Its use and default behaviour depend on the implementation/application.
TIME-WAIT timer Maintains the active closer in TIME-WAIT so delayed segments expire and the final acknowledgment can be repeated if required.
Delayed ACK timer Allows an acknowledgment to be briefly delayed so it may be combined with outgoing data or another acknowledgment, while avoiding excessive delay.

Retransmission timeout (RTO)

TCP estimates the round-trip time (RTT) from acknowledged segments and uses the estimate and its variation to set an RTO. A timeout that is too short causes unnecessary retransmissions; one that is too long delays recovery from loss.

RTO is based on smoothed RTT (SRTT) and RTT variation (RTTVAR)

In commonly used TCP algorithms, the RTO calculation uses a smoothed RTT plus a safety margin based on RTT variation. Exact constants and rules are specified by the TCP implementation/standard and should not be confused with a fixed universal timeout.

9. UDP Characteristics, Header Structure and Applications

Definition

User Datagram Protocol (UDP) is a connectionless transport protocol. It sends independent datagrams without establishing a connection. UDP provides process-to-process delivery using port numbers, but does not itself guarantee delivery, ordering, duplicate suppression or retransmission.

Characteristics

  • Connectionless: no handshake is required before sending datagrams.
  • Message-oriented: each send operation produces a datagram; message boundaries are preserved.
  • Low protocol overhead: UDP has a fixed 8-byte header.
  • Best-effort delivery: datagrams may be lost, duplicated or delivered out of order.
  • No built-in flow control or congestion control equivalent to TCP's mechanisms. Applications using UDP must behave responsibly and implement additional mechanisms when needed.
  • Supports unicast, multicast and broadcast use where supported by the network and application.

UDP header format

UDP header: four fields of 16 bits each, for a total of 8 bytes.

Field Size Function
Source Port 16 bits Identifies the sending application; may be zero when not used by the sender.
Destination Port 16 bits Identifies the receiving application.
Length 16 bits Length in bytes of the UDP header and UDP data; minimum value is 8 bytes.
Checksum 16 bits Detects errors in the UDP header and data; calculation includes an IP pseudo-header. It is optional in IPv4 but required in IPv6 except for narrowly defined exceptions.

Applications of UDP

  • DNS: Many standard DNS queries use UDP; TCP is also used in defined situations.
  • DHCP: Uses UDP for client-server address configuration.
  • VoIP and real-time media: Often use UDP to avoid waiting for retransmission of delayed media packets; application protocols may add their own recovery/congestion mechanisms.
  • Online games: May use UDP for time-sensitive updates.
  • Streaming and real-time communication: UDP may be used where the application manages timing and loss handling.
  • QUIC: Runs over UDP and provides transport features, including reliability and congestion control, above UDP.

10. TCP Flow Control Using Sliding Window

Meaning of flow control

Flow control prevents a sender from transmitting more data than the receiver can buffer. TCP uses a byte-oriented sliding-window mechanism. The receiver advertises its available receive buffer space in the TCP Window field; the sender limits the amount of unacknowledged data accordingly.

How TCP sliding-window flow control works

  1. The receiver allocates a receive buffer for incoming bytes.
  2. The receiver advertises a receive window (rwnd), representing the amount of additional data it can accept.
  3. The sender may transmit bytes within the permitted window without waiting for an acknowledgment for every segment.
  4. As the receiver accepts data and the application reads it, buffer space becomes available.
  5. The receiver advertises an updated window, allowing the sender's window to slide forward.

Receive window and congestion window

The sender is constrained by two different limits:

Effective sending window = min(rwnd, cwnd)
  • rwnd (receiver window): Advertised by the receiver; protects the receiver from buffer overflow.
  • cwnd (congestion window): Maintained by the sender's congestion-control algorithm; helps protect the network from overload.
Do not confuse: Flow control protects the receiver. Congestion control protects the network. Both can limit how much data the sender may have in flight.

11. TCP Congestion Control

Meaning of congestion

Network congestion occurs when the offered traffic load approaches or exceeds the capacity of network resources such as router links and buffers. It can cause long queueing delays, packet loss and reduced throughput.

Causes

  • Too many sources transmit simultaneously.
  • Traffic arrives at a router faster than its outgoing link can transmit it.
  • Insufficient buffer capacity causes packet drops.
  • Retransmissions add more traffic and may worsen congestion.
  • Uneven traffic distribution creates bottlenecks even when other links are underused.

Congestion control in TCP

TCP congestion control adjusts the congestion window (cwnd), which limits the amount of unacknowledged data in the network. TCP interprets signals such as packet loss and ECN marking as indications of congestion and changes its sending rate.

Flow control versus congestion control

Flow Control Congestion Control
Protects the receiving host. Protects the network from excessive traffic.
Based mainly on receiver buffer availability. Based on network congestion signals such as loss, delay or ECN.
Uses the receiver-advertised window (rwnd). Uses the sender's congestion window (cwnd).
Prevents receiver buffer overflow. Reduces overload, queue growth and packet loss.

12. Slow Start, AIMD and Congestion Avoidance

Slow Start

TCP begins with a congestion window (initial cwnd) and increases it as acknowledgments arrive. During slow start, cwnd grows approximately exponentially per round-trip time: it increases by roughly one segment for each new acknowledgment, resulting in a doubling per RTT when acknowledgments arrive for all segments. Slow start continues until a threshold (ssthresh) is reached or congestion is detected.

Congestion Avoidance

When cwnd reaches ssthresh, TCP generally enters congestion avoidance. Instead of exponential growth, cwnd increases approximately linearly, commonly by about one maximum segment size (MSS) per RTT. This slower growth reduces the risk of suddenly overloading the network.

AIMD — Additive Increase / Multiplicative Decrease

  • Additive Increase: When no congestion is detected, increase cwnd gradually, approximately linearly.
  • Multiplicative Decrease: When congestion is detected, reduce cwnd by a multiplicative factor. A common TCP response to loss is to reduce the congestion window substantially, often approximately by half, subject to the specific TCP variant and event.
AIMD: increase cwnd additively; decrease cwnd multiplicatively when congestion is detected.

Conceptual graph only; it illustrates exponential growth, linear growth and a multiplicative reduction. It is not a measured TCP trace.

Typical response to congestion

  1. TCP increases cwnd during slow start or congestion avoidance.
  2. A congestion indication occurs, for example packet loss detected by duplicate ACKs or a retransmission timeout.
  3. TCP reduces cwnd and updates ssthresh according to its congestion-control algorithm.
  4. TCP resumes transmission more cautiously, using congestion avoidance or slow start depending on the event and algorithm.
Exam distinction: Slow Start is exponential growth; Congestion Avoidance is approximately linear growth; AIMD describes additive growth and multiplicative reduction.

13. DECbit and RED Congestion Avoidance

DECbit

DECbit is an early congestion-avoidance mechanism associated with Digital Equipment Corporation's network architecture. It uses a congestion indication bit in packet headers. A router experiencing congestion marks packets by setting the bit. The destination echoes the indication to the source, and the source adjusts its sending window according to the fraction of marked packets.

Working of DECbit

  1. A router monitors its queue length.
  2. When the average queue exceeds a specified threshold, the router sets the congestion indication bit in forwarded packets.
  3. The destination returns the indication to the sender in acknowledgments.
  4. The sender examines the proportion of marked packets over a measurement interval.
  5. If a significant fraction is marked, the sender reduces its congestion window; otherwise, it cautiously increases the window.

RED — Random Early Detection

Random Early Detection (RED) is an active queue-management technique used in routers. Instead of waiting until a queue becomes full, RED monitors the average queue length and probabilistically drops or marks packets before the buffer overflows. This early signal encourages responsive transport sources to reduce their sending rates.

Working of RED

  1. The router calculates a smoothed average queue length.
  2. If the average is below the minimum threshold, packets are normally enqueued.
  3. When the average lies between the minimum and maximum thresholds, packets are dropped or marked with an increasing probability.
  4. When the average exceeds the maximum threshold, packets are typically dropped or marked according to the configured policy.
  5. Responsive senders detect loss or ECN marking and reduce their congestion window.
DECbit RED
Uses an explicit congestion indication bit that is echoed back to the sender. Uses average queue length to make probabilistic early drop/mark decisions.
Sender adjusts its window based on returned congestion indications. Transport sources react to early packet loss or ECN marking.
Associated with the DECnet congestion avoidance scheme. Active queue management technique for routers.
Signals congestion through packet marking. Signals congestion probabilistically before the queue becomes full.
Terminology: RED is a queue-management mechanism, not a replacement for end-to-end TCP congestion control. DECbit is a historical explicit-feedback approach.

14. SCTP — Stream Control Transmission Protocol

Definition

Stream Control Transmission Protocol (SCTP) is a reliable, message-oriented transport protocol. It combines features useful for transporting messages and supports multiple streams within an association and multihoming (multiple network addresses at an endpoint).

Characteristics and features

  1. Message-oriented: Preserves message boundaries, unlike TCP's byte-stream service.
  2. Reliable transfer: Uses acknowledgments, checksums and retransmission to provide reliable delivery.
  3. Multistreaming: Supports multiple independent streams within one association, reducing the impact of ordering delays between unrelated streams.
  4. Multihoming: An endpoint can be associated with multiple IP addresses, providing path redundancy and resilience.
  5. Association setup: Establishes an association using a four-way cookie-based handshake (INIT, INIT-ACK, COOKIE-ECHO, COOKIE-ACK).
  6. Congestion and flow control: Includes mechanisms to control traffic and protect the receiver and network.

TCP, UDP and SCTP comparison

Feature TCP UDP SCTP
Connection model Connection-oriented Connectionless Association-oriented
Data model Byte stream Datagrams / messages Messages
Reliability Reliable, ordered byte delivery No built-in reliability guarantee Reliable message delivery
Multistreaming No native independent streams within one connection No Yes
Multihoming Not a native standard TCP feature Not provided by UDP itself Yes
Typical use Web, file transfer, email DNS, DHCP, real-time applications Telecommunication signalling and applications needing its features

15. Quality of Service (QoS)

Definition

Quality of Service (QoS) refers to the ability of a network to provide predictable or differentiated service levels for traffic according to application requirements. Different applications have different needs: voice and video are sensitive to delay and jitter, while file transfer places greater emphasis on reliable delivery and throughput.

QoS parameters

Parameter Meaning Importance
Bandwidth / throughput Available capacity or achieved data-transfer rate. Important for high-volume video, downloads and data transfer.
Delay (latency) Time taken for data to travel from source to destination. Low delay is important for interactive voice, video and gaming.
Jitter Variation in packet delay. High jitter can disrupt real-time audio and video playback.
Packet loss Fraction or number of packets that fail to reach the destination. Loss can degrade media quality and reduce transport throughput.
Reliability Consistency and dependability of successful communication. Important for business-critical data and transactions.

QoS mechanisms and techniques

  • Traffic classification and marking: Identifies traffic classes and marks packets so network devices can apply policies.
  • Scheduling: Determines which queued packet is transmitted next; examples include priority scheduling and weighted fair queuing.
  • Traffic shaping: Smooths traffic by buffering packets and controlling the transmission rate.
  • Traffic policing: Checks traffic against a rate profile and may drop, remark or otherwise handle excess traffic.
  • Admission control: Determines whether a new flow can be accepted without violating existing service commitments.
  • Resource reservation: Reserves or allocates resources for selected flows where the architecture supports it.
  • Active queue management: Uses early drop or marking strategies such as RED to manage queue build-up.
Example: A voice call generally needs low delay, low jitter and low packet loss. A large file transfer can tolerate more delay but benefits from high throughput and reliable delivery.
